# Contributing

How to change this repo without breaking the cluster or the docs. Commits go straight to `main`; CI ([`.github/workflows/validate.yml`](../.github/workflows/validate.yml)) is the gate, and Flux applies `main`.

## Agent-assisted changes

Use the [software change workflow](software-change-workflow.md) to agree an outcome, observable contracts, design boundaries, authority and evidence with a coding agent. It includes an operator quick start, a reusable task-record template and an illustrative promotion-preview proposal. Invoke it explicitly in your request; it is a procedure, not an installed command or permission to commit or deploy.

## Validation

Run before every push:

```bash
make check
```

`check` runs `check-repo` (renders every active Flux path, validates Kubernetes and Flux schemas, SOPS structure, shell syntax, required substitutions, required Secret files and settings, and relative Markdown links; never contacts the cluster), `test` (the unit tests in `tests/`), `check-apps` (compiles every `v2-records` instance and compares the files Git holds with what they render, the comparison `make check-v2` makes, then checks that each app record's team is registered, that the notify routes are the registry's, and that the template fixtures pass the app contract; it needs Go), `check-otel` (validates the rendered collector configs with the collector release they will run; `swhurl/otel.py`), `check-lint` (Ruff and ShellCheck at the versions CI pins) and `check-docs` (compares the [workstream registry](workstreams.md) and its status pages with Git; `swhurl/docs.py`). `make check` runs them in parallel and keeps each one's output together. It leaves out `check-templates` (every stack template combination's `swhurl.yaml` through `app-new` and the app contract; reads the templates from GitHub), which takes minutes on the shared 4-CPU host and runs in CI on every push: run it locally when a change touches a template pin (`STACK_REVISIONS`), the app types or what `app-new` writes, so a refusal shows before the push. GitHub Actions runs the rendering and fixture checks in parallel jobs, alongside the operator tests, lint and dry runs. For a pull request whose complete diff only changes `apps/<app>/...`, `clusters/home/app-*.yaml` and/or the unit list `clusters/home/kustomization.yaml` (so a new app and a first promotion qualify), CI skips the template and OTel checks and the tooling job; none of the three reads the unit list, which `check-repo` builds; the tests' sample instance is the frozen copy in `tests/fixtures/instance/`, and a change there is not app-only. App policy and manifest/schema validation still run. A mixed, empty or unclassifiable diff runs the full workflow, as do pushes to `main`. A pull request or push that changes only apps' input records (`app.yaml`, `release.yaml`, `instance.yaml`, `offers/`, encrypted files; `tools/ci_changes.py`) is rendered with `make app-sync` in the workspace before `check-repo` and `check-apps`, so it is checked as `main` will hold it once the [Render workflow](../.github/workflows/render.yml) has rendered it; any other change is checked as committed, so a commit that leaves rendered files stale still fails. The offline collector fixture allows up to 30 seconds for startup and processing under parallel load, stopping as soon as its records flush. The OTel job caches checksum-verified collector binaries; the template job caches Copier's `uvx` environment. Template sources are shallow-cloned once per stack during each check.

Prerequisites (CI pins the same): `kubectl`, `helm`, `uv`, Go 1.26 for `check-v2` and `check-apps` (the version `v2/go.mod` states), Python 3 with the `check` dependency group from [`pyproject.toml`](../pyproject.toml) (PyYAML), and `flux-schema`. `make test` and `make console-dev` run in the environment `uv` builds from `uv.lock` (the `check` and `console` groups); after changing a group, run `uv lock` and commit `uv.lock`:

```bash
go install github.com/fluxcd/flux-schema/cmd/flux-schema@v0.9.0
export PATH="$(go env GOPATH)/bin:$PATH"
```

CI downloads the same version's release binary and checks its SHA-256 (`.github/workflows/validate.yml`); bump the URL and checksum together.

CI also runs every `DRY_RUN=true` target and `REQUIRE_HELM=1` so Helm-based tests cannot silently skip. `make check-secrets` needs the age key, so it runs locally only.

## Operator tooling

**Bounded Go exception:** the offline v2 model, compiler and preview comparator are a separate module in [`v2/`](../v2/go.mod), with Go-native tests and direct CLI invocation, outside the Python command catalogue. External-effect adapters need separate approval; v1 retains all rules below. The [phase-1 contract and build instructions](iteration-2-plan.md#2-phase-1-model-and-contract) are canonical. `make check` does not run Go checks: run `make check-v2` (format, vet, tests and v2's [design guardrails](iteration-2-plan.md#guardrails)) as well as the applicable v1 checks. CI runs it in the tooling job, with Go set up from `v2/go.mod`, the chart v2's profile pins fetched first and `REQUIRE_HELM=1`, so its manifest check cannot skip.

**Code graph exception:** the read-only [code graph](visual-change-tool.md) development aid is a separate standard-library package in [`devtools/codegraph/`](../devtools/codegraph), outside `tools/` so it is not in the console image. It reads Git through its own revision reader instead of `Runner`, is not a `swhurl` command, and never imports or runs the code it analyses. `make check-codegraph` runs its tests (part of `make check` and CI); `make check-lint` lints it. Its [primitives and contracts](visual-change-tool.md#4-primitives-and-contracts) are canonical.

All v1 operator logic lives in the Python package [`tools/swhurl/`](../tools/swhurl) (live tests in `swhurl/livetests/`), run as `python3 -m swhurl <command>` with `tools/` on `PYTHONPATH`; the Makefile's `$(SWHURL)` does that. A command that edits apps or needs the other locked dependencies is marked `uv=True` in [`swhurl/commands.py`](../tools/swhurl/commands.py) and `make` runs it through `uv run --frozen`; `make` stays the operator interface. Choose the language by what the code does:

- **Python** for anything that parses JSON or YAML or edits structured files, makes a safety decision or refusal, handles or compares Secret values, polls or cleans up after failure, or produces a pass/fail verdict.
- **Bash** for short linear glue, a streaming pipe nothing inspects, code that runs where Python dependencies are not guaranteed (the host timer installer, [`host/install-timer.sh`](../host/install-timer.sh), and its systemd unit templates), and command lists that double as documentation (`tests/fixtures/apps.sh`). Kept bash uses `set -Eeuo pipefail`, has a dry-run path where it changes anything, and passes `make check-lint`; when it grows real logic, the logic moves to `swhurl` and the script calls it.

- Call external tools only through `swhurl.run.Runner`. It handles `DRY_RUN` (pass `mutating=True` for changes), redacts registered Secret values from every message, and can hide a command's output from errors (`secret_output=True`). Read output live, line by line and redacted, with `Runner.stream(args)` (closing it stops the command). Stream sensitive data with `Runner.pipe(producer, consumer)`: the processes share an OS pipe Python never reads, and either side failing raises (like `pipefail`). Pass credentials on stdin (`input=`), never in argv: `clickstack.py` sends mongosh and API scripts this way, and backups give `mongodump` its login as a config file on stdin.
- Report through `swhurl.report.Report` (`[OK]`/`[BAD]`/`[WARN]` and the exit code).
- A reader that asks many independent things (a console page) wraps its runner in `swhurl.run.SharedReads`: inside `once()` an identical `kubectl get` runs once, and `runner.together(...)` runs independent reads at once (a plain `Runner` runs them one after another, so a command in a terminal is unchanged). At most three run at a time (`READ_SLOTS`): each is a `kubectl` process of about 56 MB, and the console's pod has 256 Mi. Nothing is kept from one page to the next, and only `kubectl get` is shared.
- A long-running reader in a pod (the console) gets its runner from `swhurl.kube.runner()`: there a `kubectl get ... -o json` that `kube.api_read` understands is one request to the API server as the pod's service account (4 to 16 ms where starting `kubectl` takes 50 to 120 ms), with kubectl's output shape and error wording, so callers and `FakeRunner` tests are the same for both. Changes, logs, Secrets and any kind missing from `kube.RESOURCES` still run `kubectl`; outside a pod (`make console-dev`, every `make` target) everything does. `RESOURCES` states each kind's API version, which `kubectl` would look up: a test compares it with the manifests in Git, and another fails when a console page makes a read that is not translated. Add a kind there when a page starts reading it.
- Unit-test with `swhurl.run.FakeRunner`: it records calls and answers from argv-prefix rules, and fails on any unexpected command.
- A new command is a function `(argv) -> int` with one entry in [`swhurl/commands.py`](../tools/swhurl/commands.py): its name, the make variables that become its arguments, its help line, what it touches (`LOCAL`, `GIT`, `READ`, `CLUSTER`, `THROWAWAY`, `GITHUB`, `HOST`), whether it needs `uv` and what `DRY_RUN=true` does (`PLAN`: prints a plan and touches nothing, which `make test` then proves; `READS`: reads without changing). Add its name to `COMMANDS` in the Makefile and a row to [commands](commands.md); `make help`, the usage line for a missing variable and `python3 -m swhurl`'s list follow from the entry, and `tests/test_commands.py` fails when the Makefile or the row differs. A name starting `check` must be `LOCAL` and one starting `verify-` must be `READ`. A `CommandError` a command does not handle is printed as one `[ERROR]` line by the dispatch.
- Words: app, environment, instance and unit are defined in the [glossary](../GLOSSARY.md); a container's settings are **variables**; the app another app calls is its **callee**; "service" is kept for what the platform provides, in the console too: one **Deployments** list serves the person using an app, the developer connecting to it and the operator (the app page's Use, Connect and Operate parts). Commands are verbs (`set_calls`) and policy rules are `check_*`.
- Layout: `run.py` and `report.py` (foundation); `commands.py` (every command, stated once); `interface.py` (stdlib-only app interface names, label primitive and catalogue checked against [apps](apps.md#platform-provided-interface)); `platform.py` (repository paths and Flux unit discovery); `bots.py` (how Render, Deploy, the console's merge gate and Validate's console image pin push to `main`, and the `bot-render` and `bot-deploy` commands those workflows run); `apps/` (`state.py`, an instance's one live verdict from the facts `ops.py` reads; `instance.py`, an app in one environment: its names, its folder and how one is recognised, using the standard-library-only name grammar from `model/records.py`; `declaration.py`, an app's `swhurl.yaml`: its fields, which are read once and which again, its one validation and its one fetcher; `contract.py` rules shared by `new.py`, which generates an instance, and `policy.py`, which checks it; `calling.py` and `events.py` for what calls and events are named and allowed; `helmrelease.py`, accessors for live HelmReleases and validators examining rendered output (Git semantics come from records); `cli.py`, argument parsing, terminal input, exit codes and post-command checks for app edits; `edit.py`, the operations that read inputs, change records and invoke the writer (promote, scale, expose, set calls, events or team, remove); `transitions.py`, pure record/list transformations shared by the operations; `errors.py`, the shared `EditError` refusal with no non-standard-library dependencies; `model/`, the [app model](plan.md#24-code-simplification--design-contracts-18-october-2026): an instance's records and shared name/kind/exposure/database vocabularies (`records.py`), pure call/event declarations and evaluation (`relations.py`), one module per capability that renders its part, `render.py`, `write.py` (allocates ports, retained storage and NATS identities during preparation, plans ciphertext and derived files together, and writes what the platform derives, for `make app-sync` and every edit command); `ops.py` for live status); `verify.py` (the list of live checks and what runs them; each check is a function beside what it checks: `flux.py`, `clickstack.py`, `apps/checks.py`, `notifications/checks.py`, `console/checks.py`, `dashboards.py` and the backup modules), `kube.py` (how a Kubernetes object's Ready condition and a CronJob's last success are read), `yamlio.py` (every YAML read and every generated file written: PyYAML's safe loader and dumper through libyaml, which made the verifier's tests about three times faster and rendering instances about eight; `apps/yaml_file.py` keeps comments and layout for a file an edit command saves, and reads one it does not save with `yamlio`), `validate.py`, `settings.py`, `secrets_check.py`, `lifecycle.py`, `clickstack.py` (first-run bootstrap; every MongoDB script, each printing one `RESULT` line, and HyperDX API access, all over stdin), `backupset.py` (a backup set: the names of its archives and metadata files, which is newest, its age, retention, checksum and S3 upload), which `recovery.py` (MongoDB backup and restore test), `sqlite_backup.py` and `sqlite_restore.py` fill and read; `notifications/` (`notice.py`, a message for a person: its one shape, the ntfy sender, the recorded sender tests use and the one reader of the platform topic; `evaluate.py` decides what the checker says, `delivery.py` works through an outbox, `service.py` is the notify service, `heartbeat.py` the host timer); `livetests/`; `console/` (the web console: `cluster.py` reads, `actions.py` runs background jobs (reconcile, suspend, resume) and finishes them before the pod stops, `jobstore.py` keeps their records in a ConfigMap, `github.py` is the GitHub REST client and reads open console PRs, their checks and merges, and the team and channel registries on `main`, `proposal.py` prepares and judges proposed record changes from a downloaded snapshot of `main` using that snapshot's tooling, then publishes only the action's owned inputs through GitHub REST, `stages.py` says how far a change has got from Git's facts (`render_targets`) and the cluster; `merge.ACTIONS` owns branch names, commands, input ownership and merge rules; `server.py` builds the app and the `Context` (`context.py`) its route groups share, each group in `routes/` (`pages`, `instance`, `teams`, `activity`, `new_app`) lists its routes with `routes(ctx)`, and `templates/` render them; see [plan](plan.md) section 7). Its image is [`images/console/Dockerfile`](../images/console/Dockerfile), built from the repository root (`podman build -f images/console/Dockerfile .`; `.dockerignore` admits only what it copies). On each push to `main`, [`validate.yml`](../.github/workflows/validate.yml)'s `console-image` job builds it alongside the checks and pushes it to `ghcr.io/samclement/swhurl-console`, tagged with the commit SHA and `src-<hash of its inputs>`, and skips the build when that hash is already published. `make console-image` (`swhurl/images.py`) computes the same hash and pins that image; a test checks it matches the workflow's shell.
- Console pages: Jinja templates in `tools/swhurl/console/templates` and one stylesheet, [`static/console.css`](../tools/swhurl/console/static/console.css). Use its colour roles (`--ok`, `--attention`, `--critical`, `--accent`) and type sizes rather than new values, the `state` and `icon` macros in `_status.html` for a status or an icon, and `data-confirm="what will change"` on a form that stops or removes something. No CSS framework and no build step: htmx, the fonts and the icons are files in `static/`, listed with their licences in [`static/LICENSES.md`](../tools/swhurl/console/static/LICENSES.md); pages load nothing from another host (tested). A page that only shows state joins `SELF_REFRESHING` in `server.py`.
- Tests import `swhurl` directly (`from swhurl import ROOT`); `make test` puts `tools/` on `PYTHONPATH` and runs [`tests/run.py`](../tests/run.py), one test per job across worker processes, or one whole class when it has `setUpClass` (or its module `setUpModule`) so that setup runs once (`-j N` sets the count, `-v` lists jobs, `-k PATTERN` or `make test K=PATTERN` runs only the classes whose dotted name contains it) and ends with the slowest classes. To run one file: `PYTHONPATH=tools uv run --frozen python -m unittest tests.test_verify`. `test_command_safety.py` is the only place that uses fake executables, for what only a real process shows; everything else uses `FakeRunner`.
- The Makefile holds one rule for every command with a function (`swhurl make <target>` builds the arguments) and recipes only for sequencing and the host timer script: no shell `if`/loops, `sed`, `grep` or `jq`. Use `make` functions (`$(if)`, `$(foreach)`) for plain sequencing and move anything else into `swhurl`.
- Operator commits require the full `make check`. The console's trusted auto-merge gate uses manifest/schema and app-policy checks on the exact merge result after restricting its diff to one new app or promotion and its unit registration; tooling tests read frozen fixtures and the other check inputs are unchanged. See [the merge gate](console.md#auto-merge).

## Checklist for a change

- **Where it goes:** a shared capability gets its own directory and Flux unit in `clusters/home/infra.yaml` or `platform.yaml`, with explicit `dependsOn`, `deletionPolicy: Orphan`, substitution only if its manifests use `${...}`, and decryption only if its path holds `*.sops.yaml`; add its row to the [Flux units table](architecture.md#flux-units), which `make check-repo` compares with Git (`platform.units()` is the inventory code and tests read). Apps use `make app-new`.
- **Secrets:** beside the consumer, following the [Secret rules](operations.md#secrets); add a `.sops.yaml` rule for any new path.
- **Checks:** for a live invariant, write one function beside what it checks, add it to `CHECKS` in [`tools/swhurl/verify.py`](../tools/swhurl/verify.py) with a sentence saying what passing means, and copy that row into the [operations table](operations.md#check-health) (unit-tested in `tests/test_verify.py`, against the fake cluster in [`tests/fakecluster.py`](../tests/fakecluster.py), which has one part per area) and `tests/` for anything checkable offline. Prefer declarative wiring over new feature switches (`SKIP_VERIFY` is the only one).
- **Live proof:** for behaviour that only shows on the cluster, add or run a throwaway test like `make live-test-lifecycle`, then record what you saw, with the date and commit, in [current state](current-state.md).
- **Charts:** pin `version:` in the HelmRelease and keep the file and its HelmRepository under `apps/`, `clusters/`, `infra/` or `platform/`, where [Renovate](operations.md#chart-updates) finds them.
- **Root units** in `clusters/home/flux-system/kustomizations.yaml` are not reconciled by Flux; run `make flux-bootstrap` after changing them.
- **Generator changes:** regenerate the fixtures (`rm -rf tests/fixtures/apps && tests/fixtures/apps.sh`); `test` fails if they drift. `tests/fixtures/instance/` is a hand-kept sample for the edit, promotion and drift tests and is not regenerated.

## Diagrams

Diagrams are Mermaid blocks in the page they explain; GitHub renders them, so there is nothing to generate or commit besides the text. Keep external systems outside the cluster subgraph, label only the edges that carry meaning, and show `Let's Encrypt (ACME)` wherever cert-manager appears and the telemetry path (app → OTel collector → ClickStack) in the container view. To check a diagram locally: `npx -y @mermaid-js/mermaid-cli -i diagram.mmd -o diagram.svg`.

The [repository blueprint](repository-blueprint.html) is the one generated diagram: a self-contained page built from a JSON model by the `repository-blueprint` skill's `build_blueprint.py`. To change it, open the page, take the model from **Edit DSL** → **Download**, edit it and rebuild; evidence links are relative to `docs/`.
